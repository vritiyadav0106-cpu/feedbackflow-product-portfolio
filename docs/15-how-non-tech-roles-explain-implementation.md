# 15 — How to Explain the “Coding” Part (Non-Tech Product Roles)

Use this when interviewers ask about implementation, technical skills, or “did you build this yourself?”

Works for **Product Manager** and **Product Analyst** applications.

---

## The one sentence answer

> “I’m not an engineer — I owned the **product** end-to-end and shipped a **functional prototype** from my PRD to validate the workflow. On a real team, engineering would own production code; I’d own discovery, requirements, and metrics.”

---

## Reframe: what you’re showing

| Interviewer might think | What you actually show |
|-------------------------|----------------------|
| “Can they code?” | “Can they **think in products**?” |
| “Is this a dev portfolio?” | “This is a **case study with a demo**” |
| “Did they overstep?” | “They know where **PM/PA ends** and eng begins” |

**FeedbackFlow proves:**
- Problem selection & scoping
- PRD + user stories
- Prioritization (RICE)
- Metrics design
- Roadmap thinking
- Ability to drive something to **“shipped”** (even as prototype)

---

## Scripts by question

### “Did you write the code?”

> “No — and that wasn’t the goal. I wrote the PRD, defined acceptance criteria, and used AI-assisted tools to implement a thin MVP so I could **demo the workflow** in conversations. I understand what the prototype does — validation rules, RICE formula, data model — but I’d partner with engineering for a production build.”

### “How technical are you?”

> “I’m **product-literate**, not engineering-literate. I can read a spec, discuss tradeoffs with eng, and explain our data model at a conceptual level. For deeper implementation I rely on engineering — which is how I’d operate on the job.”

### “Why not just use slides?”

> “Slides don’t test the **loop**. I needed to know: can a PM actually go from feedback → feature → score → decision in under 10 minutes? A clickable prototype answered that faster than a deck.”

### “Walk me through the architecture”

> “Three layers: the **screens** users see, the **rules** like RICE scoring from my PRD, and **local storage** so data persists without a backend. I deliberately skipped auth and APIs — that’s v2 once the workflow is validated. I documented this the same way I’d hand off to engineering.”

---

## 5 concepts to know (30 min study)

Read [`08-technical-overview-for-pms.md`](08-technical-overview-for-pms.md) — you only need:

1. **Why browser-only** — speed + lean validation  
2. **Where data lives** — localStorage = demo only, not team product  
3. **RICE formula** — your business rule, not “random code”  
4. **Core loop** — capture → promote → score → sort  
5. **v2 eng asks** — database, auth, integrations  

---

## Product Analyst angle (extra line)

> “As an analyst, I’d care that every screen maps to a **metric** — inbox volume, promotion rate, % scored backlog. The dashboard isn’t decoration; it’s the measurement layer for whether prioritization is actually happening.”

---

## What NOT to say

| Avoid | Say instead |
|-------|-------------|
| “I’m a full-stack developer” | “I shipped a prototype from my PRD” |
| “I coded everything alone” | “I owned product; tools helped implement my spec” |
| Apologizing for being non-tech | “I chose the fastest way to validate the hypothesis” |
| Reading code line-by-line | Demo the product live |

---

## Practice checklist

- [ ] 30-second honest answer memorized  
- [ ] 5-minute demo without mentioning code  
- [ ] One sentence on what eng would build in v2  
- [ ] Link metrics to dashboard (PA angle)
